# AI辅助开发记录协议

## 记录目的

将“使用了AI”拆解成可核查的任务、交互与验证结果。不收集完整Prompt，不把采纳数量解释为收益，不将工具品牌与表现因果绑定。

## 开始前

1. 建立需求、Issue与任务验收标准，选择7种任务类型之一。
2. 在使用AI前记录预计总工时；这是主观估计，不是实验对照。
3. 确定AI参与环节和需要人工验证的风险，例如日期边界、重复导入、权限与秘密信息。

## 交互后

- 每个可辨识的交互阶段记录一条AIInteraction，写工具、目的、Prompt摘要与建议摘要。
- Prompt次数是实际发起请求次数；建议数量是预先统一粒度的独立建议条数。不要把代码行当建议数。
- accepted_count为实际进入实现/方案的建议数，未采用为0；人工修改轮数单独计数。采纳但需修改仍可算采纳，应说明修正。
- estimated_before_hours/actual_hours为该交互阶段的估计和实际用时；任务actual_hours为总工时，**不自动将两者相加**，以免重叠。
- 没有可靠计时就保留任务未完成/实际时间未知，并在文档中解释；不要补造分钟数。演示耗时只能进入demo。

## 验证后

记录TestResult完整套件总数与通过数；首轮失败后修复要另建一次运行，不覆盖首轮。发现Defect后记录发现/解决时间。任务返工次数按已完成阶段被重新打开的轮数记录；普通编辑不算返工。最后写Retrospective及下一步行动，并关联真实Commit/PR。

## 信息最小化

API拒绝常见GitHub/OpenAI Token形态、Bearer长串和私钥头，且422不回显输入。但规则不是完整DLP，不能检测所有秘密/隐私。提交者必须先删除邮箱、姓名、客户标识、内部URL和业务原文，使用“某边界输入”“某测试用例”等描述。GitHubToken仅在.env或部署密钥环境中，不写入交互记录。

## 本项目开发证据

参见case-studies。当前案例来自本次实际AI编写、测试和修复，不声称有人类逐行修改；用户提供了流程约束、仓库选择与产品语义反馈。没有人工对照实验，所以没有真实效率提升百分比。
