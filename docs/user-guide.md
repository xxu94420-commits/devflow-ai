# 使用指南：从一个需求开始

DevFlow AI帮助你回答三个问题：这件事是否说清楚了、开发进行到哪里、AI建议最后有没有被采用。它不能替你决定业务规则，也不会自动完成开发。

## 首次访问者：先试一次需求评估

1. 打开[在线演示](https://devflow-ai-demo.onrender.com)，进入左侧“需求质量评估”。免费服务闲置后首次打开可能较慢。
2. 上方例子是人工编写的模拟说明。向下找到“在线试用需求评估”，在“模型连接”选择已配置的模型。
3. 填写需求名称、需求描述和验收条件。“验收条件”就是怎样判断功能做好了，例如“文件格式错误时说明哪一行有问题”。不知道的条件可以留空，不必编造数字。
4. 只填写公开或脱敏内容，阅读接收方并勾选同意发送，再点“开始真实AI评估”。
5. 对照每条原文，阅读模型指出的问题和需要确认的事项。认可问题就填写理由并采纳，不适用就说明原因并驳回。采纳问题不等于需求已经修复。
6. 根据业务实际情况修改输入，再评估一次，比较问题是否被澄清。服务设有调用间隔和每日额度；显示失败时，不代表评估通过。

公网试用只临时展示结果，刷新或离开页面可能丢失，不适合保存工作记录。项目看板仍然只读。没有模型可选时，可以先读模拟示例。

## 自己持续使用：本地记录完整过程

本地启动与模型配置由开发者按README和[配置说明](requirement-review.md)完成。业务使用者只需操作页面：

1. **保存需求**：选择项目，写清目标和验收条件，保存需求。
2. **评估与确认**：选择模型，确认发送；逐条采纳或驳回，写下自己的判断理由。
3. **修订**：手动修改正文，填写修改原因，保存为新版本并重新评估。旧版结果保留，不能直接用于确认新版。
4. **交给开发**：创建关联任务。预计工时只是计划；完成后由开发者填写有依据的实际工时。
5. **记录证据**：开发者关联代码提交、PR和测试；人工AI记录只写摘要，不放密钥和敏感提示词。
6. **复盘**：查看任务时间线和周报，说明哪些建议有帮助、哪些需要修改。样本少时先积累记录，不急着宣称效率提高。

## 看板中的常见词

| 页面用词 | 可以这样理解 |
|---|---|
| Issue | 仓库里的一张问题或工作单 |
| Commit | 一次有记录的代码修改 |
| PR | 提请检查和合并的一组代码修改 |
| 测试通过率 | 已实际执行且有结果的测试中，通过的比例 |
| 样本量 n | 本次统计实际使用了多少条记录 |
| Demo | 明确标注的模拟数据，用来学习界面 |
| Live | 真实仓库活动和人工记录，不代表数据一定齐全 |

“—”或“未知”表示证据不足，不是零；模型没有发现问题也不等于需求完整。不要把模拟看板数字写成真实企业成果。
